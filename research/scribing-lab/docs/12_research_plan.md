# 12 Research Plan

## 目的

この研究の目的は、テキストからペンプロッタ向けの日本語筆記軌跡を生成し、紙面上で自然に見える出力を実現することである。

最終目標は、人間の手書きと判別されにくい文章出力である。ただし、到達は一度で行うのではなく、短い改善サイクルを何度も回して品質を高める。

## 研究方針

この研究は、次の方針で進める。

- 主評価は preview に置く。
- 実機スキャンは後段の確認に限定する。
- 当面は自動評価よりも、人間の目視確認と口頭フィードバックを優先する。
- 既存の `human_abx` 基盤を使い、候補を並べて比較しながら feedback を回収する。
- failure tag による機械的な判定は補助に留め、主ループは人間の見え方で回す。
- 研究は一度で完成させるのではなく、`Plan` / `Do` / `Check` / `Act` を繰り返して改善する。

## 当面の到達目標

最初に目指すのは、最低限の正常な文字を安定して出力できる状態である。

具体的には、次を満たすことを当面の目標とする。

- 文字が読める。
- 画順が破綻しない。
- 文字が潰れない。
- preview 上で明らかな崩れがない。
- 短文でも極端に機械的に見えない。

## 評価の考え方

評価は、段階ごとに役割を分ける。

### 主評価

- preview の見た目
- human_abx による相対比較
- 人間による口頭フィードバック

### 補助評価

- trajectory metrics
- failure tag
- preview の比較指標

### 後段確認

- 実機スキャン
- scan と preview の差分確認

この順序を守ることで、実機確認を毎回行わずに FB ループを速く回せるようにする。

## テスト対象文字セット

評価入力は少数の固定例に限定せず、常用文字を広く含む 100 種類以上の文字・文章を用意する。

### 方針

- 単文字だけでなく、短文・中長文・長文を含める。
- かな、漢字、数字、記号、Latin を混ぜる。
- 同じ文字でも、文頭・文中・文末・反復など位置差を含める。
- 実際の文章として読める入力を優先する。
- 常用範囲を広く網羅し、局所的な最適化に偏らないようにする。

### 構成

- 単文字群
  - ひらがな
  - カタカナ
  - 常用漢字
  - 数字
  - 記号
- 短文群
  - 挨拶文
  - 説明文
  - 依頼文
  - 日常文
- 中長文群
  - 複数文からなる説明
  - 文章中に記号や数字を含むもの
  - 同一文字の反復を含むもの
- 長文群
  - 段落を含む文章
  - 行送りや字間が観察しやすい文章

### 最低条件

- 100 種類以上の入力を持つこと
- 常用文字を広く含むこと
- 単文字と文章の両方を含むこと
- 反復文字と文脈差を含むこと

## 研究サイクル

研究は 1 回で終わらせず、短い PDCA を繰り返す。

1. `Plan`
   - 次に直す点を 1 つだけ決める。
2. `Do`
   - 最小変更を入れる。
3. `Check`
   - preview を human_abx で見せる。
   - 人間の口頭 FB を回収する。
4. `Act`
   - FB を反映し、次の改善点を 1 つ決める。

このループでは、複数の大きな変更を同時に入れない。改善点と結果の対応を追えることを優先する。

## フェーズ

### Phase 0: 最低限の正常出力

目的:

- 壊れていない文字を安定して出す。

作業:

- 文字構造辞書の最低限を整える。
- レイアウト破綻を避ける。
- 画順の維持を確認する。
- preview で読めるかを確認する。

完了条件:

- `永` と基本かなが安定して出る。
- 明らかな文字化けや欠落がない。

### Phase 1: preview 中心の human FB ループ

目的:

- 人間が見て違和感を指摘できる状態を作る。

作業:

- `human_abx` で候補を並べる。
- 各候補に対して口頭 FB を取る。
- FB を次ラウンドの修正方針に変換する。

完了条件:

- 1 ラウンドごとに改善点が 1 つ定まる。
- 比較対象が毎回揃う。
- 人間の見え方を基準に改善が進む。

### Phase 2: 常用文字の安定化

目的:

- 常用文字を広く含む入力で、基本的な可読性を保つ。

作業:

- かな・常用漢字・数字・記号・Latin の破綻を減らす。
- 単文字だけでなく短文でも確認する。
- 文字の潰れ、欠落、過剰な揺れを抑える。

完了条件:

- 常用文字を含む広いセットで極端な破綻が少ない。
- 100 種類以上の評価入力を回せる。

### Phase 3: 反復改善の安定運用

目的:

- 改善を継続的に回せる状態にする。

作業:

- `Plan` / `Do` / `Check` / `Act` を固定運用する。
- 人間 FB から次の変更点を明示する。
- 変更と改善の対応を残す。

完了条件:

- 改善履歴が追える。
- 口頭 FB が次の実装に結び付く。

### Phase 4: 補助評価の導入

目的:

- 人間 FB が安定してから、自動評価を補助として使う。

作業:

- preview の比較指標を参照する。
- trajectory metrics を補助情報として見る。
- failure tag は分析補助として扱う。

完了条件:

- 人間評価と補助評価の役割分担ができる。
- 自動評価が修正方針の参考になる。

### Phase 5: 実機確認

目的:

- preview で十分に改善した候補のみ、実機で確認する。

作業:

- preview と human_abx で候補を絞る。
- 必要時のみ実機スキャンを取る。
- scan と preview の差分を監査する。

完了条件:

- 実機スキャンが FB ループを遅くしない。
- 実機は確認工程として位置づく。

## 失敗の扱い

当面は failure tag を主役にしない。

理由は、初期段階では「どのタグか」を厳密に詰めるより、まず人間が見て最低限の正常出力に到達することが重要だからである。

ただし、後段で分析しやすいように、必要最低限のメモとしては残す。

## 成果物

- baseline の固定条件
- 100 種類以上の評価入力セット
- preview ベースの比較記録
- human_abx の比較結果
- 口頭 FB を反映した改訂履歴
- 必要時のみの実機スキャン記録

## 成功条件

- 常用文字を広く含む入力セットで、まず読める出力ができる。
- preview 中心で改善サイクルを回せる。
- human_abx と口頭 FB で次の変更が決まる。
- 実機スキャンを毎回行わなくても、研究が前進する。
- 改善が PDCA の反復として追跡できる。
